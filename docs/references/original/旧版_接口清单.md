# 接口清单

演示里 `页面Demo/js/store.js` 的每一个 `S.xxx` 方法，都对应下面的一个接口。风格用常见的「资源加动作」写法，具体路径、版本号、认证细节由研发定。返回格式统一为 JSON；错误统一为 `{ "错误": "给用户看的中文一句话" }` 加合适的状态码，**凡是演示里已有的提示，文案原样沿用**（在 `页面Demo/js/store.js` 与 `views_b.js` 里可以查到）；演示里没有、因为接了真后端才需要的提示（例如「这不是你的目标」），文案由研发按同样的口吻补写：短、说人话、告诉对方下一步怎么办。前端原样显示服务端返回的那句话。

约定：

- 所有接口都要登录（除了登录和设置密码两个）。未登录返回 401。
- 「今天」由服务端提供，所有接口返回里附带 `今天`。
- 日期是 `YYYY-MM-DD`，月份是 `YYYY-MM`。
- 权限不够：对**页面类数据查询**返回 404 或空结果（不暴露存在性）；对**写操作**返回 403。
- 写操作都在一个事务里完成，且同事务写修改记录。

## 一、登录与账号

| 接口 | 说明 | 权限 |
|---|---|---|
| `POST /登录` 入参：姓名、密码 | 成功后设置 HttpOnly 会话 Cookie，返回当前用户 | 公开 |
| `POST /退出` | 清除会话 | 登录 |
| `GET /我` | 返回当前用户：id、姓名、部门、权限（管理员、业务线负责人、成员）、负责的业务线、「成员能看公司总进度」设置、今天 | 登录 |
| `GET /邀请/{令牌}` | 校验邀请链接是否有效，返回姓名 | 公开 |
| `POST /邀请/{令牌}/设置密码` 入参：密码 | 设置密码并自动登录，令牌作废 | 公开 |
| `POST /成员/{id}/重置邀请` | 重新生成邀请链接，并让旧会话失效 | 管理员 |

安全要求：密码哈希用带盐的慢哈希；登录失败要限速（例如同一姓名五次失败锁定十分钟）；会话有效期建议三十天，改密码或停用后立即失效；Cookie 加 `HttpOnly`、`SameSite=Lax`，上线用 HTTPS 时加 `Secure`；邀请令牌足够随机，一次性，七天过期。

## 二、填报（成员最常用）

### 我的填报页

`GET /我的填报?月份=2026-12`

返回：我这个月的每条目标，每条带：目标 id、业务线、项目、类型、单位、角色、岗位目标说明、目标、累计、完成度、时间进度、灯、**待填**、最近填报日、领先指标名称、统计口径提醒。另外返回 `统计截止`、`上月月末结算`（若有待填的上月目标，按同样结构返回）。

对应演示：`V.fill`。字段含义见 `02_业务规则.md`。

### 新增填报

`POST /填报` 入参：

```json
{ "目标id": 77, "日期": "2026-12-20", "金额": 8.5, "风险": "达人档期延后", "领先指标": 3 }
```

服务端校验：

| 校验 | 失败时的提示 |
|---|---|
| 目标存在且有效 | 找不到这条目标 |
| 目标属于我；管理员可代填 | 这不是你的目标 |
| 金额是有限数字 | 请填一个数字 |
| 日期在目标所在月内，且不晚于今天 | 日期不在本月，或还没到 |
| 风险不超过八十字 | 风险请控制在八十字以内 |
| 目标月份未来月不允许填报 | 这个月还没开始 |

返回：新记录 id，和更新后的这条目标（累计、完成度、灯）。前端据此更新卡片，并展示「已记下」提示和「撤销」按钮。

对应演示：`S.addEntry`。

### 撤销与恢复

`POST /填报/{id}/作废` 、 `POST /填报/{id}/恢复`

权限：本人写的，或管理员。作废后不计入任何统计，但记录保留。

对应演示：`S.voidEntry`。

### 我的记录

`GET /我的记录?条数=40`

返回最近四十条，每条：id、业务线、项目、类型、日期、金额、风险、是否作废。

对应演示：`V.mine`。

## 三、总览与下钻（业务线负责人、管理员）

所有「看」的接口，服务端先按身份过滤目标行（管理员全部；业务线负责人是自己负责的那几条业务线的所有行；成员只有自己的行（成员只在「填报」「我的记录」「自己那条目标的详情」里出现）），再计算。

### 总览

`GET /总览?月份=2026-12`

返回：统计截止、已过天数、本月天数、时间进度；若干「类型卡」，每张卡含：类型 id、名称、单位、目标（管理员为公司月目标，没设则为分配合计）、已分配合计、累计、完成度、偏差、状态、灯、预计月末、需关注项数、「分下去的与公司目标差多少」；总的「需关注项数」「本周还没填的项数」。

权限：管理员；业务线负责人（范围受限）；成员只在「成员能看公司总进度」打开时返回**合计卡**，且不含「需关注」「待填」等明细。

对应演示：`V.overview`、`R.aggregate`。

### 类型页

`GET /类型/{类型id}?月份=` 返回合计卡，加按业务线的列表（业务线 id、名称、人数、合计、需关注项数）。对应 `V.metric`。

### 业务线页

`GET /业务线/{业务线id}/类型/{类型id}?月份=` 返回合计卡，加每个人的目标行（含第一条预警原因）。对应 `V.line`。

### 人页

`GET /成员/{id}/目标?月份=` 返回该成员本月所有目标行。权限：管理员；业务线负责人只能看到自己业务线内的行。对应 `V.person`。

### 单个目标详情

`GET /目标/{id}`

返回：目标行（全部计算字段）、所有已到的检查点及每个检查点的偏差和灯、前三个已结月的完成度、最近十二条填报记录（含作者、是否作废）、本人是否可撤销。权限：目标的负责人、该业务线负责人、管理员。对应 `V.goal`。

### 关注

`GET /关注?月份=`

返回两组：「需要关注」（灯非灰，且原因不为空，红先于黄，同色按落后多的在前）、「这周还没填」（待填且没有预警）。仅当月有「这周还没填」。对应 `V.attention`。

### 趋势

`GET /趋势?类型=&维度=业务线或人&月数=6`

返回：月份列表；每一行的名称、各月完成度、各月灯、是否本月（未结束）、是否持续低效、低效月数；最后一行合计。权限：同总览；业务线负责人只含自己业务线的行。对应 `V.trend`、`R.trend`。

## 四、工作台（仅管理员，其余一律 403）

### 目标

| 接口 | 说明 | 对应演示 |
|---|---|---|
| `GET /工作台/目标?月份=&类型=` | 返回该月该类型的公司月目标、已分配合计、差额，按业务线分组的目标行 | `V.adminGoals` |
| `PUT /公司目标` 入参：月份、类型、数值 | 设置或修改公司月目标，数值不小于 0 | `S.setCompanyTarget` |
| `POST /目标` | 新增一条目标，字段：月份、负责人、类型、业务线、项目、角色、目标、岗位目标说明、统计口径提醒、每周顺带记的数 | `S.addGoal` |
| `PATCH /目标/{id}` | 改目标数字、负责人、角色、业务线、项目、说明；**类型不可改** | `S.updateGoal` |
| `DELETE /目标/{id}` | 软删除，置无效 | `S.removeGoal` |
| `POST /工作台/复制上月` 入参：从、到 | 目标月完全没有有效目标时才执行；跳过已停用成员；同时复制公司月目标 | `S.copyMonth` |

校验与提示：

| 场景 | 提示 |
|---|---|
| 目标数字小于 0 或不是数字 | 请填大于等于 0 的数字 |
| 同月同人同类型同业务线同项目已有 | 这个人在这条业务线、这个项目上已经有目标了，请直接改那一条 |
| 改完与另一条重复 | 改完会和另一条目标重复，请检查 |
| 目标月已有目标，仍要复制 | 这个月已经有目标了 |
| 月份晚于本月加两个月 | 最多提前排两个月 |

改动目标数字时，**修改记录的文字要带前后值**，例如「品牌负责人 · 锅气玛特自营 · GMV：目标 250 → 260」；如有「原因」入参，附在括号里。`PATCH` 支持可选入参「原因」。

### 成员

| 接口 | 说明 | 对应演示 |
|---|---|---|
| `GET /工作台/成员` | 全部成员（含停用），带状态（已激活、还没设置密码、已停用）和角色标签 | `V.adminPeople` |
| `POST /成员` 入参：姓名、部门 | 新增，返回邀请链接。姓名为空提示「请填写姓名」；重名提示「已经有「某某」」 | `S.addMember` |
| `POST /成员/批量` 入参：文本，一行一人 | 逐行新增，返回成功数和失败行说明；重名跳过 | `bulkmember` |
| `PATCH /成员/{id}` 入参：姓名、部门、权限 | 改资料；改成员权限时，若会导致没有管理员，拒绝：「至少要保留一位管理员」 | `S.updateMember` |
| `POST /成员/{id}/停用` 入参：接手人 id | 见下 | `S.deactivateMember` |
| `POST /成员/{id}/启用` | 重新启用 | |

停用逻辑（同一事务）：

1. 若他是最后一位管理员，拒绝：「至少要保留一位管理员」。
2. 若他本月及以后有有效目标，必须传接手人，否则拒绝：「这个人还有目标，请先选接手人」。
3. 把这些目标转给接手人；若会违反唯一约束，拒绝并列出冲突的目标。
4. 他负责的业务线转给接手人（没有接手人则置空）。
5. 置停用，使他的所有会话失效。
6. 写修改记录：「停用成员：某某，N 条目标转给某某」。历史月份目标与历史填报不动。

### 类型与业务线

| 接口 | 说明 | 对应演示 |
|---|---|---|
| `GET /工作台/类型与业务线` | 全部类型和业务线（含隐藏） | `V.adminTypes` |
| `POST /类型` 入参：名称、单位 | 名称不能为空、不能重名。提示：「请填写名称」「已经有同名的目标类型」 | `S.addMetric` |
| `PATCH /类型/{id}` 入参：名称、单位、显示 | 同上校验 | `S.updateMetric` |
| `POST /业务线`、`PATCH /业务线/{id}` 入参：名称、负责人、显示 | 提示：「请填写名称」「已经有同名的业务线」 | `S.addLine`、`S.updateLine` |
| `POST /排序` 入参：对象（类型或业务线）、id、方向（上或下） | 与相邻项交换顺序 | `S.move` |

### 规则

| 接口 | 说明 | 对应演示 |
|---|---|---|
| `GET /设置` | 全部规则参数 | `V.adminRules` |
| `PATCH /设置` 入参：键、值 | 校验数值范围（健康线与预警线都不大于 0 且预警线不大于健康线；观察期、断更、连续落后、持续低效为正整数；低效线在 0 到 1 之间） | `S.setSetting` |
| `POST /设置/恢复建议值` | 全部恢复默认 | `S.resetSettings` |

### 修改记录

`GET /修改记录?条数=60` 返回最近若干条：说明、操作人、日期、时间。对应 `V.adminLog`。

## 五、辅助

| 接口 | 说明 |
|---|---|
| `GET /健康检查` | 返回 ok，供部署监控使用 |
| `GET /导出?月份=` | 管理员：导出某月目标与填报，格式为表格文件。这是备份与对账用，第二期可做 |
| 备份 | 数据库定时备份（至少每天一次），保留近三十天。由部署方实现，不在本接口清单内 |

## 六、统一的返回结构：「目标行」

以下字段在各个查询接口里反复出现，建议后端封装成一个统一结构（字段名对应 `期望结果.json` 的「目标行」，括号里是演示代码里的字段）：

| 字段 | 含义 |
|---|---|
| id | 目标 id |
| 月份 | `period` |
| 类型 id、类型、单位 | `metric_id`、`metric`、`unit` |
| 业务线 id、业务线、项目 | `line_id`、`line`、`project` |
| 负责人 id、负责人、部门 | `member_id`、`owner`、`dept` |
| 角色 | `role` |
| 岗位目标说明、统计口径提醒、领先指标名称 | `duty`、`guard`、`lead_name` |
| 目标、累计、完成度、时间进度、偏差 | `target`、`done`、`comp`、`progress`、`dev` |
| 状态、灯 | `status`、`level` |
| 原因（列表）、需要关注 | `reasons`、`attention` |
| 最近风险、风险日期 | `risk`、`risk_date` |
| 最近填报日、距今天数、断更 | `last_date`、`since`、`stale` |
| 应填日、待填 | `due`、`pending` |
| 连续落后次数、各检查点偏差 | `streak`、`cp_dev` |
| 前几个月完成度 | `hist` |
| 近三月低效月数、持续低效 | `low_months`、`persistent` |
| 预计月末 | `projected` |
| 填报条数 | `entries` |

**服务端是这些字段的唯一计算方。** 前端不要自己再算一遍，否则两边会不一致。

## 七、并发与幂等

- 填报：同一人短时间重复点击「提交」，前端要禁用按钮；服务端对「同一目标、同一日期、同一金额、同一作者、十秒内」的重复请求，当作同一次提交（幂等），避免重复入账。
- 改目标数字：用「最后写入生效」即可；规模很小，不需要乐观锁。但修改记录里要如实记下前后值。
- 复制上月：用事务，重复点击第二次会因为「已有目标」而拒绝。

## 八、权限测试清单（必须覆盖）

后端上线前，用不同身份各跑一遍：

1. 成员 A 请求成员 B 的目标详情 → 404。
2. 成员请求总览（设置为「不能」）→ 404 或空；设置为「能」→ 只有合计，没有明细。
3. 成员请求「关注」「趋势」「人页」→ 404。
4. 业务线负责人请求其他业务线的目标、人页 → 404；请求本线的 → 成功。
5. 成员、业务线负责人调用工作台任一接口 → 403。
6. 成员对别人的目标 `POST /填报` → 403。
7. 成员对别人写的记录 `作废` → 403；对自己的 → 成功。
8. 被停用的成员，旧会话立刻失效。
9. 最后一位管理员不能被停用，也不能被改成成员。
10. 业务线负责人（同时是成员）：总览、关注、趋势、角标只含他负责的业务线；他在别的业务线上的自己的目标，只出现在填报页和该目标详情里，不出现在总览、关注、趋势。
