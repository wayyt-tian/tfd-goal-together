# 绩效系统设计审查：50–80 人

审查日期：2026-11-23。审查对象为当前可运行工作台及七个核心页面，依据本次实际截图、交互验证和隔离数据测试。附件是参考资料，用户最新确认的范围是「结果目标＋责任人份额」。

结论：这套两级组织、目标份额、本人增量反馈的工作方式适合 50–80 人的小型组织。本次已把默认浏览方式改为概况、搜索、分页与逐层展开，完成目标树及必要的规模优化。当前完成的是本机可运行版本的功能验证；长期正式运行仍需要实际周期、数据存储与部署方面的补齐，不能把样本验证等同于 80 人同时在线的生产性能保证。

入口明确显示各项指标及完成度，点击数值或「查看目标拆解」进入树。保留现有品牌和状态文字，增加目标/责任人搜索、涉及组织筛选与每页 12 项。右侧预警按结果目标归并，避免同一个目标的多人预警占满列表。

原问题：大量目标与责任人同时铺开时，管理者难以辨认优先事项。现在先看指标、结果目标，再进入责任份额。

证据：改进后总览。当前业务金额由用户现有数据计算，没有为展示而修改。

## 目标与汇总规则

- 指标完成值 = 其结果目标的有效完成值之和；结果目标完成值 = 成员份额有效完成值之和；成员份额完成值 = 本人有效增量反馈之和。
- 每层完成度 = 本层完成值 ÷ 本层目标值，不平均下层完成率。目标为 0 显示未设目标，进度条封顶但文字保留超额完成。
- 公司目标 ≥ 结果目标合计，结果目标 ≥ 成员份额合计；差额显示待拆解/待分配。个人其他目标独立计量。
- 跨组织共用一条目标、同一责任份额和反馈仅计一次。部门汇总按该部门成员份额计算。
- 负责人树只计算管理范围内份额，不展示全公司未分配额度。成员只能更新自己，负责人也不能替别人改写流水。
- 撤销和未来日期反馈不计入截至值。停用人员的原有业绩仍保留在目标树中，且明确标记；有效成员名单汇总使用当前列表口径。

## 规模、权限与保存验证

独立样本：80 位成员、5 个一级部门、15 个二级部门、24 个业务结果目标、310 份责任份额、11,160 条业务反馈、80 项个人目标及 80 条个人反馈。其中一个目标关联全部 80 人。所有测试姓名与业绩均虚构，未导入实际工作空间。

已通过：

1. 总值、成员份额、未分配额度、多组织计一次、撤销与未来反馈排除。
2. 本周起点、搜索第 80 人、第 7 页及返回原列表、筛选后页码收敛。
3. 七个页面生成、列表条数限制，树中每批 12 人/5 条流水及继续加载。
4. 公司负责人、跨部门任职的一级负责人、普通成员的界面与服务端范围校验。
5. 非本人反馈修改、范围外反馈、直接删除原始流水、重复编号及公司目标越权均被拒绝；旧版本保存返回 409。
6. 使用较长但合法的反馈说明，完整快照为 5,470,629 字节；单项个人目标调整的请求为 213 字节，保存成功，11,160 条原反馈内容保持不变。
7. 浏览器验证本人填报及撤销、跨标签账号切换后同步身份、键盘 Enter 展开与 Escape 关闭后焦点返回入口；测试过程中未记录浏览器错误。

Node 字符串渲染样本中，总览约 85–150ms、成员目标约 27–30ms，其他页面约 0.5–5ms。这只是本机生成 HTML 的观测，不是浏览器帧率、网络延迟或多用户压力测试。

复现：`npm test`。`scripts/test-persistence.cjs` 自动创建、清理临时 SQLite 库，使用独立服务器。实际业务库在重启前后及最终复核通过业务、用户与部门摘要比对。
